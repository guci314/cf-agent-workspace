# 会话压缩自动化：可行方案

> 读码基准：`guci314/edgeone-agent-lab` HEAD `e7b59db`。区分【读码确认】与【推演】。

## 结论先说

**`docs/01` 第 603 行那个判断可以推翻。** 原文：

> 要补自动化，得放弃「用平台原生 Session」这个选择：在 `_host.ts` 的 `ask()` 里
> 自己读历史 + 拼 `input`，不再交给 `session`，才能塞进「超过 N 条就先压一次」的判断。

**现在代码里已经有一个每回合都跑、且拿得到全量历史的钩子** ——
`sessionInputCallback`（`_host.ts:516`，2026-09-25 为修「会话被毒死」加的）。
它就是那个「塞判断」的地方，**不需要放弃平台原生 Session**。

## 现状【读码确认】

- `openaiSession()` 是 SDK 原生 Session，**没有压缩钩子** —— 这句仍然成立
  （原版 CF 的 `compactAfter(200k)` 是 Cloudflare 私有扩展）
- 手动 `/compact` 已完整实现，逻辑全在 `src/feishu/compact.ts`（零依赖、有单测）
- 胶水在 `_host.ts:640-667` 的 `compact()`：`getItems → summarize → clearSession → addItems`
- `summarize()` 在 `_host.ts:352`，**刻意不走 `run(agent,…)`**（避免污染 session）

## 方案：挂在 `sessionInputCallback` 上

现有回调（`_host.ts:516`）：

```ts
sessionInputCallback: (history: any[], newItems: any[]) => {
  diagCounters.sessionInputCalls++;
  return sanitizeAndAppend(history, newItems, (drop) => { /* 记诊断 */ });
},
```

**它是同步的、每回合调用一次、第一个参数就是全量历史** —— 三个条件都满足。

### 但有一个真障碍：回调是同步的

`sessionInputCallback` 的返回值要**同步**给出（它是 `(history, newItems) => items`，
不是 async）。而压缩要**调模型做摘要**，那是异步的、还要几百毫秒到几秒。

所以**不能在这个回调里直接压**。可行的做法是「标记 + 下回合处理」：

```
本轮：sessionInputCallback 里只做判断（纯同步、便宜）
        if (超阈值) diagCounters.compactWanted = true
      照常返回消毒后的历史，本轮正常跑

      —— 回合跑完后（已有后台执行的落点）——
      检查 compactWanted
      if (true) → 在后台执行压缩（getItems → summarize → clear → addItems）
                 → 发一条提示「历史较长，已自动压缩」
```

**为什么这样才安全**【推演，但有代码依据】：
- 压缩要求「读到全量 → 清空 → 只写回摘要」三步原子。若插在回调里，
  `run()` 正在用那份历史，清掉会导致本轮输入凭空消失。
- 放在**回合之后**，session 处于静止态，和手动 `/compact` 的时序完全一致 ——
  **复用的是同一套已验证的逻辑**，不引入新的正确性风险。

### 阈值用什么

**不要用 token 估算**（要引入 tokenizer，依赖变重，且估不准）。
用**条数 + 字符数**，两者都能从 `history` 同步算出、零依赖：

- `items.length > N`（比如 60）
- 或 `renderTranscript(history).length > MAX_TRANSCRIPT_CHARS`（已有常量 `120_000`）

**注意 `renderTranscript` 已经是纯函数**（`compact.ts`），直接能复用。
用它算长度既有依据、又和实际压缩时看到的是同一份东西。

### 触发后怎么告知用户

在回复卡片末尾附一行，比另发一条消息好（不打断、不额外消耗 API 调用）。
文案要**点明历史被动了**，因为这是用户没主动要求的操作。

## 三个必须处理的风险

1. **压缩失败不能毁历史。** 现有实现已经防住了 —— 摘要为空时
   `return "摘要没生成出来……历史原样保留"`，**不动 session**。自动化路径必须沿用这条。
2. **别和手动 `/compact` 抢。** 若用户刚手动压完，只剩 1 条摘要项，
   `MIN_ITEMS_TO_COMPACT = 3` 天然挡住，不会重复压。
3. **钩子静默失效。** `sessionInputCallback` 是可选钩子，名字写错会静默不生效
   （`_diag.ts:79` 已经踩过这个坑，所以有了 `sessionInputCalls` 计数器）。
   自动化同样要**加一个可观测的计数器**（如 `autoCompactions`），
   否则「没自动压过」和「钩子没挂上」分不清。

## 值得先验证的事【未实测，标注为未知数】

1. **`sessionInputCallback` 的 `history` 到底给多少条？**
   若平台按窗口截断（`session-sanitize.ts` 提到「按窗口取」），
   那 `history.length` **可能永远到不了阈值** —— 自动化就成了死代码。
   **这是方案成立与否的前提，必须先测。**
2. **后台执行能不能跑到压缩那一步？**
   已知「返回 Response 后未 await 的代码能跑完」线上实测成立（`elapsedMs: 15046`），
   但那是**模型回合**；压缩是又一跳异步，要单独确认。
3. 平台对 `history` 的截断策略：是否按 token 而非条数。

## 最小改动清单【推演】

| 文件 | 改动 |
|---|---|
| `src/feishu/compact.ts` | 加一个纯函数 `shouldCompact(history): boolean`（条数或字符数超限） |
| `agents/feishu/_host.ts` | `sessionInputCallback` 里调 `shouldCompact`，置标记 |
| `agents/feishu/_host.ts` | 回合结束后检查标记 → 后台跑压缩（复用现有 `compact()` 的三步） |
| `agents/feishu/_diag.ts` | 加 `compactWanted` / `autoCompactions` 计数器 |
| `test/smoke.ts` | 测 `shouldCompact` 的边界（和现有 G 节同一套路） |

**纯函数进 `compact.ts`、胶水留 `_host.ts`** —— 这正是这个仓库现有的分层约定
（`compact.ts` 文件头明确写了这么做的理由），照它办。
