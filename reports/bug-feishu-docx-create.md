## 1. 原结论错在哪（这份记录最该留下的部分）

原报告写：「当前 `docs.ts` 导出的六个工具全部要求一个**已存在**的资源 URL」。
**在写下那一刻的代码快照里，这句是事实**；错的是从它推出「本项目缺这个能力」
之后就再没回头核过。三个具体问题：

1. **拿旧快照下结论**。判断「缺某个能力」之前没有重读一遍当前代码/工具清单。
   代码变更的节奏比这类报告的生命周期快得多。
2. **详细的代码引证增强了可信度，也延长了它的寿命**。原报告带行号、贴实现片段，
   写的人自己都会觉得「已经核实过了」。**引证的详细程度 ≠ 核实的时效性** ——
   这份报告活生生演示了一遍。
3. **缺一条证伪动作**。下结论前跑一次 `git log -1 -- src/feishu/docs.ts`、
   或直接列一遍工具清单，成本几秒钟。项目自己的 `docs/01` 里就写着
   「**先证伪自己的第一假设**，再去读实现」，这次没照做。

> 同类教训在本项目出现过第二次：`decisions.md` 那条——「提示词没说的规则，
> 模型不会遵守」。共同点是**结论一旦写下就不再回头核**。

## 2. 实测确认过的事实

全部是打真实租户 API 得到的，不是读文档推的。

| 事实 | 怎么验的 |
|---|---|
| 创建接口**只收 title**，不支持带内容创建 | 发标题 2000 字的创建请求 → 回 `99992402 field validation failed`，`field_violations` 里**只有 `title` 一个字段**，没有任何 content/children 入口 |
| 标题长度 **1~800** | 同上：2000 字 → `"the max len is 800"`；空标题 → `"the min len is 1"` |
| **应用身份本来就有创建权限** | 关键手法：**故意发参数非法的请求**。飞书网关先查权限、后校验参数，所以「拿到参数错」就等于「权限通」。对照组在「列出云盘文件」上回的是 `99991672 Access denied`（权限错）—— 两种错形状完全不同，一眼可辨 |
| **应用身份建的文档：用户能打开，但只有只读** | 建了一篇，再用浏览器**以用户身份**真点一遍 UI：正文读得到，但菜单里是「**申请编辑权限**」、点「删除」回「**无权限操作**」、往正文里打字**打不进去**。**这条推翻了一个听起来很合理的假设**——原计划据此把创建改成「用户身份优先 + 多要求一次 `/login`」，当时判定取消；后来又发现它翻出了另一半问题（见第 2.1 节） |
| 创建成功返回 `document_id` | 响应 `data.document.document_id`，拼成 `https://feishu.cn/docx/<id>` 即链接 |
| **删除的 API 只有一个入口** | `DELETE /open-apis/drive/v1/files/{file_token}?type=docx`（进回收站）。实测：`DELETE /docx/v1/documents/{id}` 与旧版 `drive/explorer/v2/file/{token}` 都是 **404，不存在** |
| 缺少的是 **scope，不是 API** | 调上面那个 delete → `99991672`，要求 `[drive:drive, space:document:delete]` 之一。**这两个 scope 是刻意不给的**（删除不可逆，见 `docs/01`） |

### 顺带挖出的一个真 bug（不属于本报告范围，一并记在这里）

同一轮实测里发现：`feishu_docx_write` 追加段落时，把载荷字段名写成了
`paragraph`，而 **docx v1 的 `block_type 2`（文本）用的是 `text`**
（`paragraph` 是旧版 `/docs/` API 的字段名）。飞书对这种错只回一个光秃秃的
`1770001 invalid param`，不说哪个字段。

**「往文档末尾追加正文」这条路从写完起就没成功过。** 它一直没暴露的原因是：
冒烟测试的断言写的是 `body.children[0].paragraph.elements[0]...` ——
**把 bug 抄成了期望值**，测试和实现出自同一份误解，于是全绿。
修法是改字段名 + 加一条显式断言钉住 `!('paragraph' in block)`。

> 教训：stub 测试能挡住「发出去的形状不对」，但**前提是期望值本身来自真实响应或
> 官方文档**，不能来自刚写完的实现。否则它只会确认你已有的误解。

## 2.1 同一个 API 行为，我推理连错两次（方向还相反）

这条值得单独记，因为它比单个 bug 更贵。

| 第几次 | 我的推断 | 实测 | 错在哪 |
|---|---|---|---|
| 第一次 | 「应用身份建的文档落在应用自己的云空间，**用户看不到**，所以创建必须走用户身份」 | 用户**看得到**（能打开、能读） | 把「应用自己的空间」直接等价成了「用户不可见」 |
| 第二次 | 「用户看得到、能渲染、有分享按钮 → **能编辑**」 | **只读**：菜单是「申请编辑权限」、打字打不进去、删除回「无权限操作」 | 把「页面正常渲染」当成了「有写权限」 |

两次我都**很确信**，两次都错，而且方向相反。共同点是：**都在用「看起来合理」代替
「真的去点一遍」**。而这两件事都只需要一个动作就能确认 —— 打开那个链接，
用真人身份把菜单里的每一项都点一次、往正文里打一个字。

> 结论：凡是「文档归谁、谁有权干什么」这类**权限语义**问题，读文档不够、推理更不够。
> 打一次真实 API（看它回的是参数错还是权限错）+ 用真人身份把 UI 操作逐个试一遍，
> 是唯一可靠的办法。

### 附：只读这件事给了「创建走用户身份」新的理由

上一节说「因为用户看得到，所以不改身份顺序」。现在多了一条相反的论据：
用户身份建的文档落在他**自己名下**，可编辑、可删除；应用身份建的则是**只读、
且谁都删不掉**（应用缺 scope、用户缺权限）。

所以这是个**未决的取舍**，不是结论：

- **应用优先**（现在的做法）：零门槛，不需要 `/login`；产出只读且清不掉
- **用户优先**：产出归用户、可编辑可删；但没 `/login` 的人用不了

（备注：本文提到的几篇实测文档因为上面这个原因**目前谁都删不掉**，
要清得先把 scope 开上。）

## 4. 官方接口调研（保留）

**飞书开放平台官方提供创建文档接口**：

- HTTP：`POST https://open.feishu.cn/open-apis/docx/v1/documents`
- 权限：`docx:document` 或 `docx:document:create`，**开启其中任意一项即可调用**
  （实测：本应用在未额外配置的情况下就已有权限）
- 支持 `tenant_access_token`（应用身份）**和** `user_access_token`（用户身份）
- 请求体：`title`（1~800 字符，纯文本）、`folder_token`（可选，不传为默认位置）
- 返回：`document_id` —— 拼上域名即为文档 URL
- 频控：**每秒 3 次**（超出返回 400 / 99991400，来自文档，未实测）

**设计要点**：该接口**只接受标题、不支持带内容创建**（官方原文：「该接口仅支持
指定文档标题，不支持带内容创建文档」）。所以创建之后**仍需**调
`POST /docx/v1/documents/{id}/blocks/{id}/children` 追加正文 ——
两步走，两者共用同一个 `appendDocxParagraphs`。

**已实现的行为**（`feishu_docx_create`）：

- 入参 `title`（必填）+ `content`（可选，换行分段）
- 内部：先建 → 拿到 id → 有 content 就追加
- **追加失败不回滚**：文档已经存在，删掉才是真的把用户的东西弄没了。
  返回里如实给 `docUrl` + `contentError`，模型可以再用 `feishu_docx_write` 补
- 标题长度、content 段数/字数都在本地先挡掉，不送给飞书换一个看不懂的 field_violations
